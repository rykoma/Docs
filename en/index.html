Microsoft Graph email attachments

Microsoft Graph documents how to retrieve message attachments in List attachments and Get attachments. You can also retrieve attachments together with messages by using a request such as /messages?$expand=attachments with List messages.

Before doing this, it is important to understand the different types of attachments in Exchange Online messages.

File attachments

These are ordinary attachments, such as an Excel file. Microsoft Graph represents them as fileAttachment resources.

When you retrieve a message with /messages, hasAttachments is true when the message has a file attachment.

Outlook item attachments

An attached Outlook item, such as a message or an event, is handled differently from an ordinary file. Microsoft Graph represents it as an itemAttachment resource.

hasAttachments is also true when a message has an attached Outlook item.

An attached eml file is a fileAttachment, while an attached msg file is an itemAttachment.

Inline attachments

These are images embedded in the message body. Images in a signature are also inline attachments. Microsoft Graph represents them as fileAttachment resources.

hasAttachments is false even when a message has an inline attachment. Because the image is embedded in the body, the body contains an img element whose src attribute has a value such as cid:f81e14a3-1bfe-491e-a2bb-e53481d97473.

The attachment can be retrieved through /attachments because it is a fileAttachment resource. Its isInline property is true, and its contentId contains the cid value from the img element’s src attribute, which allows the attachment to be matched to its position in the body.

Cloud attachments

These are attachments that contain link information, such as a link to OneDrive. Outlook no longer provides an operation to create this type of link. Microsoft Graph represents them as referenceAttachment resources.

Default Output of Remote PowerShell Commands

Note

This article is a technical record from 2018. The Exchange Online Remote PowerShell connection that uses New-PSSession is no longer available following Microsoft’s retirement of Remote PowerShell. The original procedure and code are preserved here for historical reference. For the current connection method, see Microsoft’s Connect to Exchange Online PowerShell. For details about the retirement, see Microsoft’s Deprecation of Remote PowerShell in Exchange Online.

Note

Update on August 1, 2018: Starting around May 2018, the default output of Get-Mailbox was gradually changed to Name, Alias, Database, ProhibitSendQuota, and ExternalDirectoryObjectId.

When you connect to Exchange Online PowerShell and run Get-Mailbox, the default output should contain four properties: Name, Alias, ServerName, and ProhibitSendQuota.

As you can see by displaying the Get-Mailbox result with Format-List (fl), the object has many more properties. When you run a command without specifying what to display, the properties shown by default are determined by the formatting configuration included in the PowerShell module.

To see how this is configured, first create a PSSession with the usual New-PSSession command.

Normally, you would run Import-PSSession next. This time, export the PSSession to files as a PowerShell module by using Export-PSSession.

Specify the destination folder name for OutputModule.

The command creates three files: .format.ps1xml, .psd1, and .psm1. The .format.ps1xml file defines the command’s default output. Although it has a specialized extension, it is an XML text file that you can open in Notepad or another text editor.

Open the file and search for Microsoft.Exchange.Data.Directory.Management.Mailbox. This is the data type returned by commands such as Get-Mailbox. The file shows that the default output is configured to include Name, Alias, ServerName, and ProhibitSendQuota.

As a test, replace ProhibitSendQuota with AdminDisplayVersion. Replace each occurrence in TableColumnHeader and TableColumnItem, then save the file.

Import the module with the modified format. Run Import-Module with the path previously specified for OutputModule.

Now, when you run Get-Mailbox, AdminDisplayVersion is displayed instead of ProhibitSendQuota.

Under the Hood: Exchange Online PowerShell with MFA

Note

This article is preserved as a technical record of an investigation from June 2017. The Microsoft Exchange Online PowerShell module discussed here is the older module that preceded the currently available ExchangeOnlineManagement module, and it is no longer available. The internal behavior described in this article does not apply to the current connection method. For instructions on connecting with the current ExchangeOnlineManagement module, see Microsoft’s Connect to Exchange Online PowerShell.

As described in TechNet, PowerShell connections to Exchange Online can use multifactor authentication (MFA).

I thought OAuth could not be used because of the limitations of Remote PowerShell. However, the behavior looks as if it uses OAuth. In this article, I investigate how it works internally.

When you download the module from the Exchange admin center by following the TechNet instructions, an application named Microsoft Exchange Online PowerShell is installed.

When you start the application, PowerShell opens and displays the following screen.

As described, the Connect-EXOPSSession command, which is not normally available, can be used. I use Get-Command to inspect the Connect-EXOPSSession command.

It appears to be defined only as a Function; the module has not been loaded yet. Instead, when you run Connect-EXOPSSession, it loads a module named Microsoft.Exchange.Management.ExoPowershellModule.dll, then uses the New-ExoPSSession command defined in that module to create and import a PSSession.

As with the traditional PowerShell connection, it appears to use a Remote PowerShell connection.

When I run Connect-EXOPSSession to connect, the familiar sign-in screen described in TechNet appears, and the session connects to Exchange Online. Running Get-Module after connecting shows that the module has been loaded.

The module path can also be checked.

Let’s look inside this path.

There are several files besides Microsoft.Exchange.Management.ExoPowershellModule.dll. The contents of CreateExoPSSession.ps1 show that this script is the implementation behind the Connect-EXOPSSession command.

Opening the executable Microsoft.Online.CSE.PSModule.Client.exe in ILSpy shows that it starts PowerShell.exe and runs CreateExoPSSession.ps1. The Microsoft Exchange Online PowerShell application appears to be implemented by Microsoft.Online.CSE.PSModule.Client.exe.

Microsoft.IdentityModel.Clients.ActiveDirectory.dll and Microsoft.IdentityModel.Clients.ActiveDirectory.WindowsForms.dll are ADAL DLLs, so it appears to use OAuth. To inspect New-ExoPSSession, I open Microsoft.Exchange.Management.ExoPowershellModule.dll in ILSpy.

If you have developed a PowerShell module, you know that ProcessRecord() contains the actual processing logic.

At this point, ADAL is used to obtain an access token. This confirms that OAuth is being used.

After obtaining the access token, the code performs the following processing, which is a little unusual.

The access token, which would normally be specified in the Authorization header, is used as the password in PSCredential. The code also adds a BasicAuthToOAuthConversion query parameter, which is not used for a normal connection to Exchange Online.

It appears that the server was extended to support authentication with these parameters.

Perhaps this could be called “OAuth over Basic Auth.” It seems rather forceful, but this was probably the best available option at the time.

Data Types in the Exchange Management Shell and Remote PowerShell

Note

This article describes behavior observed in 2017 in the Exchange Server Management Shell and remote PowerShell. It does not describe Exchange Online behavior.

The data types returned by the Exchange Management Shell and remote PowerShell can differ.

For example, when a transport rule has moderators configured, you can inspect them with ModerateMessageByUser. In the Exchange Server Management Shell, this is an array of RecipientIdParameter objects, which inherits from the System.Array class.

In remote PowerShell, it is an ArrayList.

This difference affects how you get the number of elements. For an array of RecipientIdParameter objects, you can use either the Length property or the Count extension method. For an ArrayList, use the Count property to get the number of elements.

Another factor is the version of PowerShell used by the remote connection client. PowerShell 2.0 does not have this issue, but version 3.0 and later can dynamically access an element’s properties and return an array.

As a result, remote PowerShell can return a value for Length even when the collection is an ArrayList. This happens because each ModerateMessageByUser element is a String, and the String type has a Length property.

In other words, when you access ModerateMessageByUser.Length in a remote PowerShell session connected from PowerShell 3.0 or later, the result is an array containing the character count of each element. It is not the number of elements.

When writing scripts, account for the data types involved.
